# 01 · 测量方法：先把「尺子」造出来

> 结论先行：**在写第一个 kernel 之前，先把测量框架写对。**
> 否则你优化了一周，拿到的数字是假的，而且不知道自己错了。

我见过（也犯过）的三种典型错误，这个框架里都刻意规避了。

---

## 一、用 CUDA Event 计时，不用 CPU 时钟

```cpp
cudaEventRecord(ev_start);
launch(...);
cudaEventRecord(ev_stop);
cudaEventSynchronize(ev_stop);
cudaEventElapsedTime(&ms, ev_start, ev_stop);
```

CPU 侧的 `clock()` / `std::chrono` 量的是「把 kernel 发出去」的耗时，不是「kernel 算完」的耗时。
GPU 是异步的，`<<<>>>` 返回时 kernel 往往还没开始跑。

**为什么用中位数而不是平均**：偶发的时钟波动、其他进程干扰会产生离群值，
平均值会被它们拉偏。取 50 次采样排序后的中位数更稳。

---

## 二、每轮之间**冲掉 L2**（这条最容易被忽略）

```cpp
// 3090 的 L2 有 6MB，这里开 256MB 的缓冲，每轮读一遍把它挤出去
void L2Flusher::flush() const {
  l2_flush_kernel<<<sm_count_ * 8, 256>>>(buf_, n_, sink_);
}
```

**不冲 L2 会发生什么**：第二次迭代时，A、B 的一部分还躺在 L2 里，于是第二次"跑得更快"。
你测到的是**缓存预热后的速度**，不是真实访存下的速度。

这个错误特别隐蔽，因为它让你的数字**变好看**——没人会怀疑一个变好的数字。

实测影响：不冲 L2 时，4096³ 的 v0-naive 能"快" 20% 以上。冲掉之后才是真实数字。

> 顺带一提，这也是为什么 `ncu` 采集出来的 `Duration` 不能直接和 benchmark 的数字比：
> ncu 会把 kernel 串行化重放，它的 Duration 普遍偏大（本项目里 v0 是 79.4ms vs 实测 62.8ms）。
> **ncu 只用来看百分比和 stall，不用来看绝对时间。**

---

## 三、cuBLAS 基线必须显式关掉 TF32

```cpp
cublasCreate(&handle);
cublasSetMathMode(handle, CUBLAS_DEFAULT_MATH);   // ← 关键
cublasSgemm(handle, ...);
```

Ampere 及以后的 cuBLAS 在部分路径上会用 **TF32**（19 位尾数）替代 FP32（23 位尾数）。
TF32 的 Tensor Core 吞吐远高于 FP32，如果基线走了 TF32，那"达到 cuBLAS 的百分之几"
就**不是同精度对比**了——你在用严格 FP32 的手写 kernel 去追一个降了精度的对手。

`CUBLAS_DEFAULT_MATH` 显式关掉 TF32，保证两边都是严格 FP32。

> 这是面试官最爱抓的一点。写简历时如果只写"达到 cuBLAS 的 X%"，一定要能说清基线的 compute type。

---

## 四、warmup：先让 GPU 把频率升上去

```cpp
for (int i = 0; i < warmup; ++i) launch(...);   // 10 次不计时
cudaDeviceSynchronize();
```

GPU 不是一直跑在最高频率的。冷启动时时钟还在爬坡，前几次迭代会明显偏慢。
不 warmup 的话，你测的是"升频过程中"的速度。

---

## 五、launch 之后必须立刻查错（不是 `cudaDeviceSynchronize`）

这是本项目踩过的坑之一，详见 [`03-踩坑记录.md`](03-踩坑记录.md)：

```cpp
launch(...);
cudaError_t e = cudaGetLastError();      // ← 必须立刻查
if (e != cudaSuccess) { /* 报出来，跳过这个版本 */ }
cudaDeviceSynchronize();
```

**只用 `cudaDeviceSynchronize()` 会漏掉配置类错误**（例如 `invalid configuration argument`、
`too many resources requested for launch`）。漏掉之后的症状是：
**kernel 根本没跑、耗时接近 0、结果全是 0，却又不报错**——非常容易被误读成"这个版本特别快"。

框架里还对运行期错误（如 `misaligned address`）做了容错：报出来然后跳到下一个版本，
否则一个版本崩掉，后面的全看不到。

## 六、正确性校验：不仅要看误差，还要看**量级**

```cpp
double err = max_abs_diff(h_c, h_ref, M * N);
// 诊断：把两者的数量级也打出来
printf("[diag] max|C|=%.3f  max|C_ref|=%.3f\n", c_max, ref_max);
```

只打印 `max_err` 是有风险的：如果内核压根没写结果、而参考结果也是 0，
你会看到 `err = 0.00e+00`，看起来「完全一致」，实际是两个空数组在比。

**加上量级诊断就能一眼识破**。本项目里真的出现过 `max_err` 全是 `0.00e+00` 的情况，
量级诊断确认了 `max|C| = max|C_ref| = 28.604`（对 K=4096、输入在 [-0.5, 0.5] 均匀分布来说数值正确），
才敢确认「逐位一致」是真的。

---

## 七、算 GFLOPS 别忘了那个 2

```
C = A(M×K) × B(K×N)
每个输出元素做 K 次「乘 + 加」= 2K 次浮点运算

GFLOPS = 2 × M × N × K / 耗时(s) / 1e9
```

`2 * M * N * K` 里的 2 是一次乘 + 一次加。漏掉它，数字会正好差一倍。
本项目 4096³ = 2 × 4096³ ≈ 137.4 GFLOP。

参考峰值：3090 的 FP32 峰值 = 82 SMs × 128 cores × 2 × 1.695 GHz ≈ **35.6 TFLOPS**。

---

## 八、完整的一次测量长这样

```cpp
L2Flusher flusher;                       // 256MB 缓冲
for (int i = 0; i < 10; ++i) launch();   // warmup
cudaDeviceSynchronize();

std::vector<double> samples;
for (int i = 0; i < 50; ++i) {
  flusher.flush();                       // 冲 L2
  cudaEventRecord(start);
  launch();
  cudaEventRecord(stop);
  cudaEventSynchronize(stop);
  samples.push_back(elapsed_ms(start, stop));
}
std::sort(samples.begin(), samples.end());
double median = samples[samples.size() / 2];
```
