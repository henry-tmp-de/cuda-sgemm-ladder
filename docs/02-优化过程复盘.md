# 02 · 优化过程复盘

> 这份文档记录的是**每一步的决策依据**：看了哪个指标 → 判断瓶颈是什么 → 做了什么 → 指标怎么变。
>
> 它不是「GEMM 优化技巧清单」，而是「一个 kernel 优化者的工作流」。

---

## 第 0 步：先算一笔账，再动手

在写任何代码之前，先搞清楚**理论上限在哪**。3090 的两个数字：

```
FP32 算力    : 82 SMs × 128 cores × 2 × 1.695 GHz ≈ 35.6 TFLOPS
显存带宽     : 936 GB/s
```

两者相除：

```
35.6e12 / 936e9 ≈ 38 FLOP / Byte
```

**含义：每从显存搬进 1 个字节，必须做大约 38 次浮点运算，否则算力就是在空等数据。**

现在看朴素的矩阵乘。算 C 的一个元素要做 2K 次浮点运算，代价是读 A 的一整行（K 个数）+ B 的一整列（K 个数）= 8K 字节：

```
实际算术强度 = 2K / 8K = 0.25 FLOP/Byte
                      vs
需要的算术强度 =            38 FLOP/Byte
```

**差 150 倍。** 所以朴素实现注定有 99% 的时间在等数据——这不是"调参能救"的问题，是结构问题。

优化的方向只有一句话：**让数据在离计算单元更近的地方被复用更多次。**

> 这一步的结论决定了整条技术路线：先做 tiling（提高复用），
> 再做向量化（减少指令数），最后做流水线（把等待藏起来）。

---

## 我的 ncu 工作流：哪个 section 回答哪个问题

优化过程中反复问自己四个问题，每个问题对应 ncu 的一个 section：

| 我想知道 | 看哪个 section | 看哪个指标 |
|---|---|---|
| 这个 kernel 是算力受限还是访存受限？ | **GPU Speed Of Light Throughput** | `Compute (SM) Throughput` vs `Memory Throughput` |
| warp 到底在等什么？ | **Warp State Statistics** + 下方的规则建议 | stall 名字（LG Throttle / MIO Throttle / Not Selected…） |
| 占用率为什么上不去？ | **Occupancy** | `Block Limit Registers` / `Block Limit Shared Mem` / `Block Limit Warps` |
| 访存效率如何？ | **Memory Workload Analysis** | L1/TEX Hit Rate、L2 Hit Rate、bank conflict |

配套的命令（`tools/profile_all.sh` 里用的就是这套）：

```bash
sudo /usr/local/cuda/bin/ncu -k "regex:sgemm_v4_kernel" --launch-count 1 \
     --section SpeedOfLight --section Occupancy --section WarpStateStats \
     --section MemoryWorkloadAnalysis --section SchedulerStats --section LaunchStats \
     ./sgemm_bench 4096 4096 4096
```

> **两个使用要点**
>
> 1. `--launch-count 1` 很重要。不加的话 ncu 会把 benchmark 里 60 次迭代全部重放一遍，慢几十倍。
> 2. **ncu 报的 `Duration` 不能当性能数字用。** ncu 会把 kernel 串行化、多次重放，
>    Duration 普遍偏大（本项目 v0：ncu 报 79.4ms，实际 62.8ms）。
>    **它的百分比和 stall 是准的，绝对时间不准。**

## v0 → naive：基准线

**做法**：一个线程算一个 C 元素，直接读全局内存。

**实测**：62.75 ms，2.19 TFLOPS，**cuBLAS 的 9.3%**

**ncu 看到什么**

```
Compute (SM) Throughput     %    94.64
Memory Throughput           %    94.64      ← 和上面一模一样
L1/TEX Cache Throughput     %    94.92
L1/TEX Hit Rate             %    94.98
```

**怎么读这个结果**：`Compute` 和 `Memory` 都是 94.64%，两个数完全相同——
这是 **L1/TEX 流水线被打满**的特征信号（三个数都贴着 94~95%）。

下方的规则建议直接点名了：

> *"each warp spends **18.3 cycles** being stalled waiting for the **L1 instruction queue
> for local and global (LG) memory operations** to be not full. This stall type represents
> about **62.8%** of the total average of 29.1 cycles between issuing two instructions."*

**判断**：瓶颈是 **LG Throttle** —— L1 的访存指令队列满了。
每做一次乘加，这个 kernel 要发出 **2 条全局 load**，指令数量爆炸。

**一个反直觉的点**：L1 命中率高达 **94.98%**，但这个 kernel 依然是全场最慢的。
说明 **"缓存命中率高" ≠ "访存高效"**——命中了同样要占用 L1 的带宽和指令发射名额。
数量太多的访存，即使全部命中，也会把 L1 流水线堵死。

**下一步的方向**：减少访存指令的数量 → 提高数据复用 → **tiling**。

---

## v1 → shared memory tiling

**动机**：v0 的诊断是"访存指令太多"。把 A、B 的一小块先搬进 shared memory，
块内线程反复读，全局访存次数就降下来了。

**做法**：32×32 的 block tile，`__syncthreads()` 分隔搬运和计算。

**实测**：47.18 ms，2.91 TFLOPS，12.3%，**相对 v0 = 1.33×**

**ncu 看到什么**

```
Compute (SM) Throughput     %    82.34
Memory Throughput           %    82.34
L1/TEX Cache Throughput     %    82.47
L1/TEX Hit Rate             %        0      ← v0 是 94.98%
```

规则建议变了：

> *"each warp spends **21.1 cycles** being stalled waiting for the **MIO (memory input/output)
> instruction queue** to be not full."*

**判断**：瓶颈**从全局访存搬到了 shared memory**。
`MIO Throttle` 说明 shared memory 的读写指令把 MIO 队列堵死了（21.1 cycles，比 v0 的 18.3 还高）。

**为什么只快了 33%**：32×32 的 tile 太小——每个 block 每轮只搬 2 KB，
而每轮要付**两次 `__syncthreads()`** 的同步代价，收益几乎被开销吃光。
而且一个线程仍然只算 1 个元素，**shared 读的次数没有减少**。

**下一步的方向**：不是 tile 更大，而是**让一个线程算多个元素**，把 shared 读的次数摊薄。

---

## v2 → 1D thread tiling

**动机**：v1 的 `MIO Throttle` 说明 shared 访存指令太多。让一个线程负责同一列的 TM=16 个元素，
这样对每个 k，B 的一个元素被读一次、复用 TM 次。

**做法**：`TM=16`，一个线程算一列的 16 个元素。

**实测**：20.25 ms，6.79 TFLOPS，28.7%，**相对 v0 = 3.10×**

**ncu 看到什么**

```
Compute (SM) Throughput     %    55.49      ← 从 82% 降下来
Memory Throughput           %    55.49      ← 从 82% 降下来
Theoretical Occupancy       %    33.33      ← 从 66.67% 掉下来
Warp Cycles Per Issued Instr   cycle  10.83 ← 从 35.87 降下来
```

规则建议：

> *"this workload exhibits low compute throughput and memory bandwidth utilization…
> each scheduler only issues an instruction every **2.7 cycles**…
> The **4.00 theoretical warps per scheduler** this kernel can issue according to its
> occupancy are below the hardware maximum of **12**."*

**判断**：MIO 的压力确实下来了（Compute/Memory 从 82% 降到 55%），
`Warp Cycles/Instr` 从 35.87 降到 10.83（warp 等待时间大幅缩短）。
**但问题换了**：占用率从 66.7% 掉到 33.3% —— 寄存器从 38 涨到 81，线程数从 1024 降到 512，
每 scheduler 只剩 4 个可发 warp。

**下一步的方向**：A 还没有被复用（算每个元素都要读一次 A）→ 改成**外积**让 A、B 双向复用。

---

## v3 → 2D thread tiling（外积）

**动机**：v2 里 B 被复用了（1 个 B 元素 × TM 次 FMA），但 A 每算一个元素读一次。
换成**外积**视角可以两边都复用。

```
内积：C[i][j] = Σ_k A[i][k] * B[k][j]        —— 一次算一个标量
外积：C[0:TM][0:TN] += A[0:TM][k] ⊗ B[k][0:TN]  —— 一次算一个 TM×TN 的块
```

每个 k：A 读 TM 次（被 TN 次 FMA 复用），B 读 TN 次（被 TM 次 FMA 复用），
**shared 读次数从 TM×TN 降到 TM+TN**。

**实测**：9.17 ms，14.99 TFLOPS，63.4%，**相对 v0 = 6.84×**（本阶梯最大的一次跳跃）

**ncu 看到什么**

```
Compute (SM) Throughput     %    59.23
Memory Throughput           %    60.86
Warp Cycles Per Issued Instr   cycle   6.27   ← 从 10.83 再降
Theoretical Occupancy       %    33.33
Registers Per Thread        register/thread  128
```

规则建议：

> *"each warp spends **2.2 cycles** being stalled waiting for the micro scheduler to select
> the warp to issue. **Not selected** warps are eligible warps that were not picked…"*

**判断**：`Not Selected` 是个**好信号**——它意味着 warp 已经准备好了、只是调度器没轮到它，
说明**延迟已经被藏得差不多了**，现在的限制是发射带宽。

**下一步的方向**：既然不是等数据了，那就**减少指令总数**→ 向量化。

---

## v4 → float4 向量化 + A 转置存储

**动机**：指令数还是瓶颈。把 4 条 32-bit 访存合成 1 条 128-bit。

**做法**：
1. 全局加载改用 `float4`
2. **把 A 以转置形式写进 shared memory**（布局从 `[BM][BK]` 改成 `[BK][BM]`）

第 2 点是关键。看计算内层要读的元素：`SA[ty*TM + m][k]`，m 递增。
在原布局下这 TM 个元素**相距 BK 个 float，不连续**，没法用 float4 读。
转置之后 `SA[k][ty*TM + m]` 在 m 方向连续，就能一次取 4 个。

**实测**：8.09 ms，17.00 TFLOPS，72.0%，**相对 v0 = 7.76×**

**ncu 看到什么**

```
Compute (SM) Throughput     %    61.04
Memory Throughput           %    76.12      ← 明显高于 Compute
L1/TEX Cache Throughput     %    79.78
Theoretical Occupancy       %    33.33
```

规则建议这次直接给了方向：

> *"**Memory is more heavily utilized than Compute**: Look at the Memory Workload Analysis
> section to identify the **L1 bottleneck**."*

**判断**：Compute 61% 而 Memory 76% —— **访存侧比计算侧更吃紧，计算单元在等数据**。
这正是流水线（双缓冲）要解决的问题。

**下一步的方向**：让"搬下一块数据"和"算当前块"重叠 → **双缓冲**。

---

## v5 → 手动双缓冲 ⚠️ 这一步**没有变快**

**动机**：v4 的 `Memory 76% > Compute 61%`，说明在等访存。双缓冲把搬运和计算重叠起来，
理论上应该直接吃掉这部分等待。

**做法**：shared memory 开两份。算 tile t 的同时，用寄存器中转把 tile t+1 从 global 取回来：

```
load tile t+1 (global -> reg)   ← 和下面的 compute 重叠
compute tile t  (smem)
__syncthreads
store reg -> smem[另一份]
__syncthreads
```

**实测**：8.10 ms，16.97 TFLOPS，**71.8%** —— **和 v4 的 72.0% 几乎相同，等于白干。**

**ncu 看到什么（这是本次项目最重要的一组数据）**

```
                    v4        v5
Compute (SM)  %    61.04     54.31
Memory        %    76.12     71.97
Achieved Occ. %    32.29     16.66     ← 腰斩
Warp Cyc/Instr     6.05      3.54     ← 改善了
Registers          125       155      ← 涨了 30
Shared Memory      16 KB     32 KB    ← 翻倍
```

规则建议：

> *"The **2.00 theoretical warps per scheduler** this kernel can issue according to its
> occupancy are below the hardware maximum of **12**. This kernel's theoretical occupancy
> (**16.7%**) is limited by the number of required registers… **Est. Speedup: 28.03%**"*

**判断 —— 两股力量在互相抵消：**

- ✅ **块内**：`Warp Cycles/Instr` 从 6.05 降到 3.54 —— **双缓冲确实起作用了**，warp 等待时间几乎减半
- ❌ **块级**：寄存器和共享内存翻倍，每 SM 能驻留的 block 从 **2 个掉到 1 个**，
  占用率 **33.3% → 16.7% 腰斩**

块内延迟藏得更好了，但 SM 上可以切换的 warp 少了一半，两者相抵，净效果 ≈ 0。

**一次对照实验坐实了这个解释**

同样的 v4 → v5，换成 1024³：

| 形状 | v4 | v5 | 变化 |
|---|---|---|---|
| 4096³ | 72.0% | 71.8% | ≈ 0（1024 个 block 抢 82 个 SM，块级并行充足） |
| **1024³** | **55.1%** | **80.9%** | **+25.8 个百分点**（总共只有 64 个 block，块级并行不足） |

**结论：双缓冲的收益不是恒定的，它取决于当前占用率。**
块级并行已经充足时，块内双缓冲没有额外价值；块级并行不足时，它才是关键。

**下一步的方向**：既然瓶颈是"寄存器/共享内存占用太高导致占用率低"，
那就找一个**不占用额外寄存器**的搬运方式 → `cp.async`。

---

## v6 → cp.async 三级流水

**动机**：v5 的双缓冲必须经过寄存器中转（`global → reg → smem`），
每条 LDG 占一个寄存器，reg→smem 还要再发一条指令。这是寄存器涨到 155 的直接原因。

**做法**：用 Ampere 的 `cp.async` 指令让数据**从 global 直接进 shared memory，不经过寄存器**：

```cuda
cp.async.cg.shared.global [smem], [gmem], 16;   // 一条指令搬 16 字节
cp.async.commit_group;                          // 把已发出的拷贝打成一个「组」
cp.async.wait_group N;                          // 等到未完成的组数 ≤ N
```

配合 **3 级流水**（比 v5 的 2 级更深）：

```
prologue: 发出 tile 0, 1
loop t:
    wait_group(1)          // 等 tile t 就绪
    __syncthreads()
    issue tile t+2         // 顺手把更远的下一块发出去
    compute tile t
    __syncthreads()
```

**实测**：7.22 ms，19.03 TFLOPS，**80.6%**，**相对 v0 = 8.69×**

**ncu 看到什么**

```
                    v5        v6
Compute (SM)  %    54.31     63.78
Memory        %    71.97     71.83
Achieved Occ. %    16.66     16.66     ← 仍然低
Warp Cyc/Instr     3.54      3.01      ← 继续改善
Registers          155       163
Shared Memory      32 KB     48 KB
```

**判断**：占用率**仍然是 16.7%**（甚至寄存器还涨了），
但 `Warp Cycles/Instr` 从 3.54 降到 **3.01** —— 流水线更深，warp 等待更少。

**关键洞察**：**占用率没有变好，性能却上去了。**
这说明 v5 的教训不能简单总结成"要提占用率"——
真正要做的是**让每个 warp 有足够的事情可做**（ILP / 流水深度）。
v6 用同样低的占用率，靠 3 级流水把延迟藏得更深，赢过了 v4 的高占用率。

**这一步的代价**：`cp.async` 只能做**原地拷贝，不能转置**。
所以 v4 那个「A 转置存放以便 float4 读」的技巧用不了了，
计算内层读 A 只能退化成**标量读**（`a_reg[m] = SA[stage][ty*TM+m][k]`，m 方向不连续）。

**下一步的方向**：既要用 cp.async、又要消除标量读带来的 bank conflict
→ **XOR swizzle**（本阶梯未实现，是自然的下一步）。

## 总结：三条可以迁移到别的算子上的结论

### 1. 瓶颈会随着优化而转移，必须每步重新 profile

```
v0: LG Throttle（全局访存指令太多）
 → v1: MIO Throttle（shared 指令太多）
 → v2: 占用率下降
 → v3: Not Selected（延迟已藏好，受发射带宽限制）
 → v4: Memory > Compute（访存侧吃紧）
 → v5/v6: 占用率成为约束
```

**每一版的瓶颈都不一样。** 如果拿着 v0 的结论（"访存太多"）去优化 v5，就是白费力气。

### 2. 占用率是手段，不是目的

- v0 占用率 **66.7%**，却是全场最慢（9.3%）
- v6 占用率 **16.7%**，却是全场最快（80.6%）

占用率的意义在于**提供足够的 warp 来隐藏延迟**。如果 kernel 本身有很深的 ILP
（寄存器分块 + 多级流水），低占用率完全可以接受。

面试被问"你的 occupancy 为什么只有 16.7%"时，正确的回答是：
> "因为这个 kernel 靠寄存器分块和 3 级 cp.async 流水提供了足够的指令级并行，
> ncu 显示 `Warp Cycles Per Issued Instruction` 只有 3.01，说明延迟已经被藏住了，
> 不需要更多 warp 来掩盖。"

### 3. 一个优化是不是有用，取决于**当前**的资源余量

双缓冲在 1024³ 上值 +25.8 个百分点，在 4096³ 上值 0。
同一个优化、同一份代码，收益完全不同。

**所以任何优化都必须带着测量去做，不能凭"这是公认的最佳实践"就上。**
