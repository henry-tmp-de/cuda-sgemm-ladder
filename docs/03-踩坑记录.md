# 03 · 踩坑记录

四个真实踩到的坑。**现象 → 排查过程 → 根因**，尤其是排查过程中我**判断错的那几次**，
因为那才是最费时间的部分。

---

## 坑 1：kernel "跑得飞快"，但结果是错的（v2）

### 现象

v2（1D thread tiling）第一次跑出来是这样：

```
v2-thread1d          0.0010 ms  134217728.3  GFLOPS  563600.0%   max_err 2.86e+01
```

耗时 **0.0010 ms**（比 cuBLAS 快 5636 倍，物理上不可能），`max_err = 28.6`（结果全错）。
**但程序没有报任何错。**

### 排查

第一反应是计时错了。但同一个框架跑 v0/v1/v3 都正常，所以是 v2 自己的问题。

在 kernel 调用之后加了一行 `cudaGetLastError()`：

```cpp
e.fn(A, B, C, M, N, K);
cudaError_t lerr = cudaGetLastError();
if (lerr != cudaSuccess) {
  printf("%-14s   !! LAUNCH FAILED: %s\n", e.name, cudaGetErrorString(lerr));
  continue;
}
```

真相立刻现形：

```
v2-thread1d   !! LAUNCH FAILED: too many resources requested for launch
```

### 根因

我给 v2 配了 **1024 线程/块**（`block(64, 16)`）。sm_86 每 SM 有 65536 个寄存器，
1024 线程时每线程最多只能分到 **64 个**。而这个 kernel 的地址计算 + `sum[16]` 累加器超过了 64 个，
于是**内核根本起不来**。

现象之所以具有迷惑性：launch 失败后，`cudaMemset` 把 C 清零了，kernel 又没写，
所以结果是全 0；计时器测到的是"什么都没发生"的时间。

### 修法

改成 **512 线程/块**（`BM=128, BN=64, TM=16` → `block(64, 8)`），
每线程可用寄存器翻倍到 128，问题消失。

### 教训

1. **`cudaDeviceSynchronize()` 不足以发现 launch 配置错误**，必须在 launch 之后立刻 `cudaGetLastError()`。
2. 看到"比理论上限还快"的数字，第一反应应该是"它在骗我"，而不是"我优化得好"。
3. 1024 线程/块看着很"满"，但寄存器预算会被压到 64 个，很多 kernel 根本放不下。

## 坑 2：`misaligned address`，我连续判断错两次（v5）

### 现象

v5（手动双缓冲）一跑就崩：

```
CUDA error: misaligned address  (src/main.cu:108)
```

### 第一次误判：以为是 lambda 的问题

第一版 v5 把「加载 / 存 smem / 计算」三段逻辑写成了 `[&]` 捕获的 device lambda：

```cpp
float4 ra[A_PER], rb[B_PER];
auto load_g2r = [&](int t) { ... ra[i] = *reinterpret_cast<const float4*>(&A[...]); };
```

我判断：lambda 捕获了局部数组 `ra`/`rb`，编译器为了取地址会把它们放进 local memory，
进而破坏地址生成。

**于是把所有 lambda 拆掉，全部内联展开（改用宏）。** 结果：**还是同样的错。**

### 第二次误判：以为是对齐声明

再想：`__shared__ float SA[2][BK][BM]` 是 float 数组，默认只保证 4 字节对齐，
而我在做 float4（16 字节）读写。于是加了 `__align__(16)`。

**结果：错误依旧。**（我甚至给已经正常的 v4 也加了这个声明，属于无效改动。）

### 第三次：用 compute-sanitizer 精确定位

停止猜测，直接上工具：

```bash
compute-sanitizer --tool memcheck ./sgemm_bench 256 256 256
```

输出直接指到行：

```
Invalid __global__ read of size 16 bytes
    at ... sgemm_v5_kernel<...>+0xf10 in v5_dbuf.cu:150
    by thread (0,6,0) in block (0,0,0)
    Address 0x7fb043406004 is misaligned
```

`v5_dbuf.cu:150` 是 `V5_LOAD_G2R(t + 1);`。

### 真正的根因（一个低级错误）

这个宏的参数**期望的是 K 方向的偏移量**（必须是 `BK` 的倍数）：

```cpp
#define V5_LOAD_G2R(T)  ...  const int gc = (T) + c;  ...
```

但我在循环里传的是 **tile 序号** `t + 1`。于是：

```
t = 0  →  gc = 1 + c   →  gc ≡ 1 (mod 4)
```

`&A[gr * K + gc]` 要求 16 字节对齐，也就是 `(gr*K + gc) % 4 == 0`。
`gc` 整体错了 1 个 float，**每次访问都错位 4 字节** —— 正好对上 sanitizer 报的
`地址偏移 4 字节` 和它推算出的 `gr=24, gc=1`。

修正只有一个字符级别的改动：

```cpp
V5_LOAD_G2R((t + 1) * BK);   // 原来是 V5_LOAD_G2R(t + 1)
```

### 教训

1. **先做量纲/单位检查再怀疑编译器。** 宏参数的语义是"K 偏移"还是"tile 序号"，
   读一遍定义就能发现；我却先去怀疑 lambda 和对齐，白折腾两轮。
2. **`compute-sanitizer` 应该更早用。** 它的输出能把问题从"某个 kernel 崩了"
   缩小到"第 150 行、偏移 4 字节"，比人肉推理快得多。
3. 报错信息里的具体数字（偏移 4 字节、`gr=24, gc=1`）是**可以直接反推根因**的线索，
   不该忽略。

## 坑 3：所有版本 `max_err = 0.00e+00`，看起来像校验坏了

### 现象

4096³ 下，**每一个版本**的误差都是 `0.00e+00`（完全一致）：

```
v0-naive       0.00e+00
v1-smem        0.00e+00
...
```

第一反应：**我的校验代码写错了**（比如比较了两个相同的数组）。

### 排查

加了一个"量级诊断"，把两个矩阵的最大绝对值也打出来：

```cpp
printf("               [diag] max|C|=%.3f  max|C_ref|=%.3f\n", c_max, ref_max);
```

输出：

```
[diag] max|C|=28.604  max|C_ref|=28.604
```

**量级是 28.6，不是 0。** 对 K=4096、输入在 [-0.5, 0.5] 均匀分布来说这个数量级是正确的
（随机游走的标准差 ≈ √K × 0.29 ≈ 18，最大值 28.6 合理）。
所以两个矩阵都是真实的非零结果，`max_err = 0` 是**真的逐位相同**。

### 为什么真的会逐位相同

所有版本按 k **升序**做 FMA 累加：

```
for tile t = 0, 16, 32, ...:
    for k in tile:  sum += a*b
```

这等价于 `k = 0 .. K-1` 的单一顺序。cuBLAS 在 4096³ 这个尺寸上也用同样的顺序且不拆 K，
所以**中间结果的舍入完全一致**，最终逐位相同。

（1024³ 下误差是 1.81e-05 —— 因为 cuBLAS 在那个尺寸换了 kernel，累加顺序不同。）

### 教训

**只打印"误差"是有风险的**：如果内核没写结果、参考结果也是 0，
`err = 0` 看起来是"完全一致"，实际是两个空数组在比。
**加上量级诊断就能一眼识破。**

## 坑 4（不算 bug，但是个大陷阱）：ncu 的 Duration 不是性能数字

### 现象

同一份代码，两边报的时间对不上：

| | benchmark 实测 | ncu 报的 Duration |
|---|---|---|
| v0-naive | 62.75 ms | **79.38 ms** |
| v6-cpasync | 7.22 ms | **8.57 ms** |

### 原因

ncu 要采集硬件计数器，必须把 kernel **串行化并多次重放**（v6 那次是 "14 passes"）。
重放时的缓存状态、时钟行为都和正常执行不同，所以 Duration 系统性偏大。

### 正确的用法

| ncu 的数字 | 能不能用来做性能对比 |
|---|---|
| `Compute (SM) Throughput` / `Memory Throughput` 等百分比 | ✅ 可以（这是瓶颈判定的依据） |
| stall reason、占用率、寄存器/smem 用量 | ✅ 可以 |
| **`Duration`** | ❌ **不可以**，用 benchmark 的数字 |

**所以本项目里的做法是**：性能表格一律来自 `./sgemm_bench`（无 ncu 附加），
ncu 只用来解释"为什么涨/为什么不涨"。

## 附：本节涉及的判据速查

| 症状 | 最可能的原因 | 第一步查什么 |
|---|---|---|
| 耗时 ≈ 0、结果全 0、不报错 | launch 配置错误 | launch 后立刻 `cudaGetLastError()` |
| `misaligned address` | 向量化访存的地址没对齐 | `compute-sanitizer --tool memcheck` |
| `max_err` 恰好为 0 | 可能是"两边都是 0"的假一致 | 加 `max\|C\|` 量级诊断 |
| ncu 的 Duration 比实测大 | ncu 串行化重放，正常现象 | 用 benchmark 的数字做对比 |
