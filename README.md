# CUDA SGEMM 优化阶梯

从最朴素的矩阵乘出发，**一版只改一个东西**，逐级爬到接近 cuBLAS。每一级都留下：
代码、性能数字、以及 **Nsight Compute 的 profile 证据**。

重点不是"我写出了多快的 GEMM"，而是 **"我怎么发现瓶颈、怎么根据 profile 反馈决定下一步"**。
完整推理链见 [`docs/02-优化过程复盘.md`](docs/02-优化过程复盘.md)。

## 结果（RTX 3090 / M=N=K=4096 / 严格 FP32）

| 版本 | 做了什么 | 中位耗时 | TFLOPS | vs cuBLAS | 相对 v0 |
|---|---|---|---|---|---|
| cuBLAS(FP32) | 基线 | 5.82 ms | 23.6 | **100%** | — |
| v0-naive | 一线程算一个元素 | 62.75 ms | 2.19 | 9.3% | 1.00× |
| v1-smem | 32×32 block tile | 47.18 ms | 2.91 | 12.3% | 1.33× |
| v2-thread1d | 一线程算一列（TM=16） | 20.25 ms | 6.79 | 28.7% | 3.10× |
| v3-thread2d | 外积二维分块（TM=TN=8） | 9.17 ms | 14.99 | 63.4% | 6.84× |
| v4-vec4 | float4 向量化 + A 转置存储 | 8.09 ms | 17.00 | 72.0% | 7.76× |
| v5-dbuf | 手动双缓冲（寄存器中转） | 8.10 ms | 16.97 | 71.8% | 7.75× |
| **v6-cpasync** | **`cp.async` 三级流水** | **7.22 ms** | **19.03** | **80.6%** | **8.69×** |
| v7-lbcap | v6 + 压寄存器提占用率（**负结果**，见下） | 7.29 ms | 18.86 | 79.4% | 8.67× |

> 所有版本与 cuBLAS 的输出**逐位一致**（`max_err = 0.00e+00`），因为在 4096³ 这个尺寸上
> 双方的 FP32 累加顺序相同、且都使用 FMA。1024³ 下差 1.8e-5（cuBLAS 在那个尺寸换了 kernel）。

### 每一级的瓶颈（Nsight Compute 实测）

| 版本 | 理论占用率 | 寄存器/线程 | 共享内存 | 主要停顿原因 |
|---|---|---|---|---|
| v0 | 66.7% | 40 | 0 | **LG Throttle** —— L1 访存指令队列满（占全部停顿 62.8%） |
| v1 | 66.7% | 38 | 8 KB | **MIO Throttle** —— shared 指令队列满（21.1 cycle） |
| v2 | 33.3% | 81 | 12 KB | 发射率低：每 2.7 cycle 才发一条指令 |
| v3 | 32.3% | 128 | 16 KB | **Not Selected** —— 有可发的 warp 但没被调度器选中 |
| v4 | 32.3% | 125 | 16 KB | Memory 比 Compute 更吃紧（L1 瓶颈） |
| v5 | **16.7%** | 155 | 32 KB | 每 scheduler 只有 **2 个 warp**（硬件上限 12） |
| v6 | **16.7%** | 163 | 48 KB | 同 v5，但 `Warp Cycles/Instr` 从 3.54 降到 **3.01** |

## 这个项目最值得说的一个发现

**加双缓冲（v5）在 4096³ 上几乎没有效果（72.0% → 71.8%），但在 1024³ 上从 55% 涨到 81%。为什么？**

因为双缓冲的代价是资源翻倍：寄存器 125→155、共享内存 16→32 KB，
于是每 SM 能驻留的 block 从 **2 个掉到 1 个**，**占用率从 33.3% 腰斩到 16.7%**。

- **4096³**：有 1024 个 block 抢 82 个 SM，块级并行本来就充足 → 块内双缓冲的收益被块级并行损失抵消，净效果 ≈ 0
- **1024³**：总共只有 64 个 block，块级并行本来就不足 → 块内双缓冲成了救命稻草

**结论：双缓冲不是无脑加分的优化，它的收益取决于当前占用率。**

### 第二个发现：ncu 的 `Est. Speedup` 预测 83%，实测 0.6%

v6 的 profile 里 ncu 给了一条建议：*"占用率 16.7% 受限于寄存器数量，**Est. Local Speedup: 83.33%**"*。

于是我加了 `__launch_bounds__(256, 2)` 逼编译器把寄存器从 167 压到 128：

| | 寄存器 | 每 SM block | 占用率 | 性能 |
|---|---|---|---|---|
| v6 | 167 | 1 | 16.7% | 78.8% |
| v7 | **128** ✅ | **2** ✅ | **33.3%**（翻倍） | **79.4%** |

**约束完全生效、占用率实打实翻倍，性能只涨 0.6 个百分点。**

因为瓶颈是 **L1 流水线的吞吐**（`L1/TEX Cache Throughput 74.81%`，而 `Max Bandwidth` 只有 41%），
不是延迟。**加 warp 只是让更多请求排在同一堵墙前面。**

> **教训：`Est. Speedup` 是启发式上限，不是预测。** 它假设 kernel 是延迟受限的；
> 一旦真瓶颈是某个饱和的流水线，它可以错上百倍。必须先看清楚假设，再用便宜实验验证。

这也顺带回答了面试常问的"你的 occupancy 为什么这么低"——
**占用率是手段不是目的**：v6 占用率只有 16.7%，却是全场最快，
因为 GEMM 靠寄存器分块提供了足够的指令级并行（ILP）。

## 环境

| 项 | 值 |
|---|---|
| GPU | NVIDIA RTX 3090（GA102, sm_86, 82 SMs） |
| CUDA | 12.8 |
| 驱动 | 570.86.10 |
| 编译 | `nvcc -O3 -arch=sm_86`，**不加 `--use_fast_math`** |
| cuBLAS 基线 | `CUBLAS_DEFAULT_MATH`（**显式关闭 TF32**，保证严格同精度对比） |

## 运行

```bash
make                 # 编译
./sgemm_bench                        # 4096^3
./sgemm_bench 1024 1024 1024         # 指定形状
./sgemm_bench --quick                # 1024^3 快速迭代
```

采集 profile（需要读 GPU 性能计数器的权限）：

```bash
sudo bash tools/profile_all.sh       # 默认 4096^3，输出到 profiles/
```
